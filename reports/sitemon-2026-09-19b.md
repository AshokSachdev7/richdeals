## Fixed inline — rot #28, and a correction to the last tick's own number

`fetchAllDeals()` in `apps/web/src/app/sitemap.ts` paged at `limit: 60` for at most **200**
iterations — a hard 12,000-deal ceiling. Past that the loop just stops: no error, no log,
the sitemap simply gets shorter while looking perfectly healthy.

The previous SITEMON report (`9e5117d`) put this "roughly 5 weeks out" at "~350/day". Both
halves are wrong, and re-deriving it is what caught them:

| | Last tick | Measured now |
|---|---|---|
| Growth rate | ~350/day | **136/day** (955 in 7 d) |
| Headroom | — | 12,000 − 10,278 = **1,722 deals** |
| Time to ceiling | "~5 weeks" | **~13 days** (≈ 2026-10-02) |

Note that "5 weeks" does not follow even from the rate that report used: 1,722 ÷ 350 is
**5 days**, not 5 weeks. A unit slipped and the number was carried forward unchecked. That
is exactly the failure mode the CEO-audit rule exists for, so it gets written down rather
than quietly corrected.

**The fix** — the bound is only a runaway guard; the loop already exits on the first page
with no `nextCursor`, so raising it costs zero extra API calls until the deals actually
exist:

```ts
for (let i = 0; i < 2000; i++) {
```

200 → 2000 = a 120,000-deal ceiling, ~2.4 years of headroom at the measured rate. Today's
regen still makes the same 172 sequential calls it made before. `tsc --noEmit` clean.
Rot #28 closed.

What this did **not** fix: the sequential paging itself. 172 calls per ISR regen is why the
route is `revalidate = 1800` instead of dynamic, and that stays true. Raising a guard that
was about to fire is not the same as making the fetch fast, and the ceiling was the part
that was about to break something.
