## The "six endpoints are byte-identical" line is retired

Prior reports concluded that only `/` drifts between prod sweeps and the other six are byte-identical,
so a `/`-only delta is never a finding. **The fresh sweep falsifies the first half of that.**

| endpoint | prior bytes | this sweep | delta |
|---|---:|---:|---:|
| `/` | 312,183 | **312,069** | **−114** |
| `/offers` | 60,233 | 60,233 | 0 |
| `/blog` | 149,049 | 149,049 | 0 |

| `/api/deals` | 40,070 | **40,109** | **+39** |

**Four moved, three held.** The "`/`-only" clause is dead. The clause that survives is the narrower
one: a `/` delta on its own is still not a finding — the homepage renders an ItemList of 30 rotating
Products, so −114 B is the rotation, and `/` actually got *faster* (0.371068 → 0.262111 s).

What changed is that a deal was pushed between the two sweeps (10808, `2026-09-21T03:58:11.466Z`).
Sitemap, feed and the API all carry deal inventory, so all three moved. The correct generalization is
not "six are frozen" — it is **"the four inventory-bearing surfaces move after a push clears ISR, and
the three static ones do not."** That is a rule with a mechanism behind it instead of a coincidence.

## Three claims from earlier reports that measurement has now falsified

**1. The cursor does NOT trail.** `telegram-2026-09-21g.md`'s CEO table says the broadcast cursor
*"now trails by one — normal external-cron lag"*. The 53rd read shows `{"lastId":10808}` against
`DB_MAX 10808` — **caught up**. The *reasoning* in `-g` was right (a gap our push opens is benign and
self-heals); the *claim that a gap exists* is wrong. It closed on its own within ~40 min, which is
`tg-broadcast-cursor-selfheals.md` holding. A prediction written earlier in this same session was
falsified half an hour later — that is the argument for re-reading the cursor file every tick instead
of carrying a sentence.

**2. The null-`productId` problem is 358 rows, not three.** Every prior report treated deal 2549's
null `productId` as one oddity beside deal 2904's Flipkart-shaped `MSCHDXPDR7BKCF3Y` and deal 10031's
hex `ae27f94b3330`. One added `count({where:{status:'LIVE', productId:null}})` returned **358** —
about **3.4% of LIVE inventory**. `-g`'s sentence *"A null `productId` on a LIVE row defeats ASIN
dedup forever"* is correct and understated by two orders of magnitude. **ASIN-only dedup is
structurally blind on 358 products**, which retroactively justifies the two-dimensional (ASIN + title)
dedup used before the Nivea push. **Routed to SEO-AUDIT-FIX: a null-`productId` guard at push time.**
This is not re-describable as three rows again.

**3. CONTENT-SEO is BEHIND pace, reversing `-f`.** `telegram-2026-09-21f.md` L122 read 1 post at
**05:51 IST** as *"ahead of pace, not behind"*. At **10:07 IST** the same single post against a 2-3/day
target is **behind**. Nothing about the post count changed — the day got older. The earlier line was
right when written and is wrong now, so it is not carried.

**Posts per day, IST:** 09-15 `3` · 09-16 `3` · 09-17 `3` · 09-18 `3` · 09-19 `3` · 09-20 `2` ·
09-21 **`1`**. Never 0, never over 4, so the hard rule is not broken — but 09-20 closed at 2 (soft
miss) and 09-21 needs two more posts. CONTENT-SEO is owed a tick and this is the second consecutive
report saying so.

**Skew wanders and is re-taken every tick:** 44/45/46/45 → 37 (`-f` L116) → 604 (`indexnow-b` L125) →
360 (`-g`) → **283 ms**. Far too small to move any timestamp finding; recorded so no report can claim
